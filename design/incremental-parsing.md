# Incremental Parsing

## Requirement

`IncrementalParser` accepts Markdown in arbitrary UTF-8 pieces. It offers two outputs, chosen when the parser is created. **Block events** are the `EventParser` events of each document-level block, subject to reference scope, emitted once the block has closed. **Progressive events** are emitted at character granularity, as soon as appended text can no longer change them, including inside open blocks and containers and before a line ends. Each property that cannot be known until later is resolved by a later event instead of delaying everything after it.

### Block events

- **Equivalence:** for any division of a source into pieces, the events emitted by all `push` calls followed by `finish` equal the events of `EventParser` for the whole source, excluding the document start and end events, provided that no reference or footnote call resolves to a definition in a later document-level block.
- **Independence of division:** the concatenated output is identical for every division of the same source, including sources with forward references.
- **No retraction:** each event is emitted exactly once, and only when no appended text can change it or any event before it. Every event emitted by `push` lies before `stable_offset`, which never decreases.
- **Reference scope:** inline content in a document-level block resolves references and footnote calls against the definitions that begin before the end of that block. A reference to a definition in a later document-level block stays literal text.
- **Block-level granularity:** stability is decided per document-level block. A block is emitted when a later document-level block begins on a line that no earlier state or lookahead can reinterpret, or when the complete lines end in a document-level blank line, or a clean ATX heading, thematic break or closed fence that closes every container. Lists, block quotes and other containers are emitted as a whole. When frontmatter is enabled and the first line opens frontmatter, all output is held back until the frontmatter closes; a first line that cannot open frontmatter, such as a code fence without an information string, holds nothing back.
- **Cost:** text without a new complete line performs no parsing. Each preparation restarts at an emitted document-level block whose line can be prepared without earlier state, so the work per completed line is proportional to the open tail of the document rather than its full length. Definitions before the restart point are borrowed from an incrementally indexed seed rather than copied or re-sorted, and finding complete lines scans only newly appended text. Work remains proportional to the length of a block that stays open, such as a long list, and of a run of blocks that depend on their predecessors, such as consecutive definitions.

### Progressive events

- **Event shape:** progressive output uses the stream's event types with these differences. A block's start event is emitted when the block opens, except as stated for paragraph-like leaves below, and has an empty span at the block's start; lists open with `tight: true` and items with `block_end: false`. Every block start is followed by a **resolution event**, immediately before the block's end, that states its full span, and for a block with a deferred property also its final tag. Inline starts, such as links and images, are emitted once decided and carry their full span. A **delimiter event** marks an emphasis or strikethrough delimiter run in place, and a resolution event later states its role. Progressive output contains no `Separator` events.
- **No retraction:** each progressive event is emitted exactly once, and no appended text can change it, any event before it, or the source it covers, other than by the resolution events for the deferred properties below. `stable_offset` is the end of the source covered by emitted events and never decreases; text after it is not yet represented. It may fall inside an open block, an open container or an incomplete line.
- **Deferred properties:** a property that appended text can still change is not stated when its block opens. The block's content is emitted meanwhile, and the property is stated by a later resolution. The deferred properties are:
  - The kind of a paragraph-like leaf. Its start is emitted with its first text that is not part of a link reference definition, so a leaf made only of definitions emits no start. It opens as `Start(Tag::Paragraph { tight: false })`, and its resolution states whether it is a paragraph, a setext heading and its level, or a paragraph whose last line is the header row of a table that follows. The last line of the leaf is a **possible header row** while the next line could still be a table delimiter row that makes it a header row of any number of cells. Only its **settled prefix** is emitted meanwhile: the text before the earliest of its first unescaped `|`, including whitespace before that `|`; the start of a code span, inline math, link, image, footnote call, autolink or raw HTML that contains that `|`, since cells are split before inline parsing; a code span or inline math that contains an escaped `|`, which a cell unescapes; and, when character escapes are disabled, any `\|`. The line ending before a possible header row is emitted as a `SoftBreak` once that line is classified as a paragraph line, even when the row is decided at the same time; reconciliation removes it if the row becomes a header. A trimmed hard break before it is emitted the same way, as a `SoftBreak`, once the row is decided to be a header. Text that a crossing construct or hard break holds is not part of the settled prefix, which begins after it; so the settled prefix is the same text as a paragraph and as the start of the first header cell. The line is decided when the next line's classification is decided. If it becomes a header row, the leaf's resolution is emitted immediately after the settled prefix, which may be empty, as for a line that begins with `|`. It states where the paragraph ends (no paragraph remains when the header is its only line, and no paragraph start has been emitted if none of the leaf's text after its definitions was, in which case the resolution has no matching start), and the spans of the table head, the header row and the first cell, and the first cell's alignment. The rest of the first cell's text follows, then its end, the remaining header cells as ordinary cell events, the ends of the row and head, and the table's remaining rows. The table's own resolution, immediately before its end, states its span.
  - The tightness of a list. Its resolution, immediately before the list's end, states `tight` for the list and the paragraphs in its items, and `block_end` for each of its items.
  - The role of each emphasis or strikethrough delimiter run: opening or closing emphasis, strong emphasis or strikethrough, partly or wholly, or literal text. Text after a run is emitted without waiting for the run to pair. A run's resolution is emitted once every character of it is decided: when its last character pairs, or immediately before its leaf's end. Pairings that involve a run on a possible header row are decided only when that line is decided, because a header row is parsed apart from the lines before it: openers on earlier lines no longer pair with it, and its own runs may then pair differently. If the line stays in the paragraph, the resolutions this decides are emitted after the soft break that ends it, or immediately before the leaf's end, in source order. If it becomes a header row, runs on earlier lines that are still unresolved are resolved immediately before the leaf's resolution, in source order, and runs in the first cell resolve as in any leaf, with the cell as their leaf; those already decided are resolved immediately after the leaf's resolution, in source order. Wherever run resolutions and a block's resolution are both emitted immediately before the block's end, the run resolutions come first, in source order. It lists, in event order, the starts, ends and literal text the run becomes.
- **Holding back:** text is held back only for the constructs listed here, and only until each is decided. Any other text is emitted once its line's block context is decided. The held constructs are:
  - inline constructs still open: a code span opener without a matching closer; an inline math opener without a closer, when math is enabled; a link or image opener, footnote call or task-list marker whose meaning is undecided; an incomplete autolink, raw HTML, entity or numeric character reference; a GFM literal autolink whose start or end is undecided, such as a word that could still become an email address or a `www.` or `http://` link;
  - an emphasis or strikethrough delimiter run at the end of the source, until the next character decides its length and flanking;
  - whitespace or a backslash at the end of the source or of a line, until later text decides whether it is trimmed or a hard break. At the end of the line before a possible header row, this lasts until that row is decided, because its becoming a header row ends the paragraph before it;
  - a word at the end of the source, when inline code information is enabled, until the next character decides whether it is the language of a code span;
  - a code span, inline math, raw HTML, link, image or footnote call that begins on an earlier line of a paragraph-like leaf and would end on a possible header row, from its opener until that line is decided, since it would become literal text if the line became a header row;
  - a line ending inside a paragraph-like leaf, until the next line's classification decides between a soft break and the end of the leaf;
  - a trailing run of `#` characters in an ATX heading, until its line ends;
  - the opening text of a paragraph-like leaf that could still be a link reference definition, from its `[` until the definition completes or fails, which can take several lines, and after it completes until the following line rules out a table delimiter row that would make it a header row; a definition that is not superseded is emitted as a `Definition` event, and the leaf's remaining text continues as before;
  - the text of a possible header row after its settled prefix, until the line is decided;
  - in a table body row, an unescaped `|` after the row's first character other than whitespace, and the whitespace before it, until the next character other than whitespace, or the line ending, decides whether it ends the row or starts another cell;
  - a line whose block classification is undecided: a possible setext underline, thematic break, list marker (including ordered markers of up to nine digits and the content indent after a marker), table delimiter row, ATX heading opener, code fence opener, math fence opener, HTML block start (a type 7 start needs the rest of its line), block quote marker, footnote definition label, or indentation that could reach four columns. A line is held only until its classification is decided, not until it ends;
  - an atomic leaf that is still open: a code block, HTML block or math block is emitted whole when it closes;
  - frontmatter, as for block events.

  Text before the earliest held construct is emitted. The text of table body cells beyond the header's cell count is dropped by the table and never emitted. A held construct releases its text as soon as it is decided, whether it completes or can no longer complete.
- **Reconciliation:** for any division of a source into pieces, the progressive output equals the events of `EventParser` for the whole source, excluding the document start and end events and with `Separator` events removed, once each block's start is given the tag and span from its resolution; a resolved header row's preceding soft break is removed, the paragraph ends before it, or its start is removed when no paragraph remains, and the table, head, row and first cell starts, with the spans from the resolution, are placed before the row's text; each list's tightness is applied to the `tight` of the list and its paragraphs and the `block_end` of its items; resolved delimiter runs become the emphasis, strong emphasis and strikethrough starts and ends, or text, that they resolved to; and adjacent text events with contiguous spans are merged. This holds provided that no reference or footnote call resolves to a definition that begins after the call.
- **Independence of division:** after merging adjacent text events with contiguous spans, the progressive output is identical for every division of the same source, including sources with forward references.
- **Reference scope:** a reference or footnote call resolves against the definitions that begin before it. A reference to a later definition, even in the same document-level block, stays literal text, because a progressive event cannot wait for the rest of its block.
- **Cost:** the total bytes examined while streaming a document, counted by the parser's examined-bytes counter in tests, which counts every byte read by the block and inline scanners, is at most a fixed multiple of the source length for each of the named cost documents in `tests/incremental_parser.rs`: a long list, a long nested list, a long block quote, a long paragraph, and a long paragraph whose text stays held behind an unclosed code span and behind unresolved link text, each streamed whole, line by line and one character at a time. The multiple is fixed in the test. No wall-clock target is set; that remains an open question.

## Rationale

Speech synthesis consumes agent replies as text deltas and needs to speak each stable sentence before the reply ends, without retracting audio it has already spoken. Replies are mostly one open paragraph or list, so block-level stability leaves them silent until they end; progressive events let synthesis start inside the first paragraph. Speech needs the text and its context (paragraph, heading, list item, quote, code, table) but not the properties that only a block's end decides, so deferring those properties rather than waiting for them removes the delay without guessing. Holding back follows the parser's own state, which keeps consumers from reimplementing inline stability with heuristics on a reparsed tail. Emphasis structure is deferred rather than held because pairing changes only nesting, not text: a stray `*` or `~` would otherwise silence the rest of its paragraph. Table header rows are deferred rather than held because any paragraph line can become one, which would otherwise hold every line until the next begins; usually only the text from a line's first `|` waits, since a line without one can become at most a single-cell header, whose text is the same as the paragraph's. Constructs that cross into a possible header row, or contain its first `|`, are held instead of deferred because the header changes what they are, not only their nesting. A hard break or such a construct before a line holds the whole line until the next one begins; that is accepted because both are uncommon in agent replies. Separators are omitted because they depend on later siblings and list tightness, and streaming consumers do not need them. Sentence boundaries and words that are still growing are decided by the consumer, not the parser. Agents often put footnote and reference definitions at the end of a reply; their calls stay literal in progressive output, so consumers such as speech must filter them.

Meeting the cost requirement means keeping the stack of open blocks and the open leaf's inline state between pushes instead of preparing the open tail again.

Block events keep exact equivalence with `EventParser` for consumers that need the final structure of each block, such as renderers. Forward references cannot be resolved before their definitions arrive; scoping references to earlier definitions keeps both outputs deterministic instead of depending on where the deltas happened to split. Progressive events scope to the reference's own position because they cannot wait for the end of the block. The progressive output was introduced for Tomori's speech synthesis in November 2026.

## Scope

`IncrementalParser`, both of its outputs, its interaction with block preparation (`Blocks::parse_from` and the recorded outline of document-level blocks), the incremental block and inline state behind progressive events, and definition lookup scoping. `EventParser`, `Document` and the HTML renderer are unchanged and continue to resolve forward references across the whole document.

## Validation

Run `tests/incremental_parser.rs`, which compares every two-piece division, character-by-character pushes and random multi-piece divisions with a single push and with `EventParser` for a corpus covering lists, nested lists, block quotes with lazy continuation, fenced and indented code, HTML blocks, tables after paragraphs, setext headings, link reference definitions, footnotes, frontmatter and CR, LF and CRLF line endings; for every `CommonMark` specification example; and for random documents built from block-opening, continuation and reinterpreting lines. Comparison with `EventParser` is limited to sources without definitions, where reference scope cannot differ; division independence is checked for all of them. The tests also check that emitted events lie before `stable_offset`, that forward references stay literal for every division, that most corpus events are emitted before `finish`, and that a first line which cannot open frontmatter holds nothing back. The unit tests in `src/incremental_parser.rs` compare random definition-heavy documents, including definitions in containers, multi-line titles, footnotes and frontmatter, with a one-shot parse whose reference scope is set per document-level block without anchors or seeds, and check that the restart point stays near the end of a long document of closed blocks.

For progressive events, run the same corpus, divisions and specification examples, and check:

- reconciliation with `EventParser` for sources without definitions, and division independence for all sources;
- that no event is retracted or changed: for every division, the merged output after each piece is a prefix of the merged final output, except that its last text event may be a prefix of the corresponding final one, and every event lies before `stable_offset`;
- release: for each held construct listed above, a test streams text through it and checks that the text before it is emitted before the construct is decided, and that the construct's text is emitted as soon as it is decided; and prose without held constructs, streamed one character at a time, is emitted up to the start of its last word within an open one-line paragraph, an open list item and an open block quote;
- deferred properties: a paragraph that becomes a setext heading; a paragraph whose last line becomes a single-cell table header, and one whose last line, streamed one character at a time, becomes a multi-cell header after its settled prefix was emitted; a header row that begins with `|`, including as a document's only paragraph line and after a definition, which emit no paragraph start; a header row after paragraph lines that arrives in one push and one character at a time, which emit the same soft break; emphasis on earlier lines and in the first cell resolved at the decision point, in order; `\|` on a possible header row with character escapes disabled; emphasis, a code span, a link and a hard break that cross into a line that becomes a header row, and the same lines followed by a line that is not a delimiter row; a code span, a link, a GFM literal autolink and raw HTML that contain a line's first `|`; a code span and inline math containing `\|` on a possible header row; and body rows with a trailing `|` and with more cells than the header; a nested list such as `- a\n  - b` followed by a loose item; a stray `*` and `~` that never pair, with the text after them emitted before the leaf ends;
- definitions: a definition that completes over several lines, one that fails on its title line, an incomplete one and a completed one each superseded by a table, and a leaf made only of definitions, which emits no paragraph start;
- cost: the examined-bytes counter over the named cost documents.

When changing block preparation, review new lookahead across lines: a line whose classification depends on a later line must not be recorded as a clean document-level boundary, and a block that can be reinterpreted by a later line must not settle the outline. For progressive events, review each new construct for earlier text that later text can reinterpret, and either add it to the held constructs or make the reinterpreted property a deferred property, with tests.
